## Local knowledge dump

This directory (`agents.d/local/`) is a **local dumping ground** for
insights, discoveries, quirks, and conventions learned during agent
sessions — anything that doesn't yet belong in the structured
`project/`, `starfleet/`, or eventual `xlibre/` taxonomies.

### Rules

1. **Dump first, sort later.** If you discover something during a
   session that is worth remembering, create or append to a file here
   immediately. Don't worry about where it should ultimately live.

2. **No cross-ship guarantees.** Other ships in the fleet may write
   here too, but there is no ordering, deduplication, or review
   process. Treat this as scratch space.

3. **Promotion path.** When a local insight proves itself stable
   (survived multiple sessions, referenced from other fragments), it
   should be moved to the appropriate taxonomy directory:
   - `agents.d/starfleet-instructions/` — fleet coordination, comms, workflow
   - `agents.d/xlibre/`   — mpbt-workspace, build system, project rules
   - `agents.d/xlibre/`    — X server, drivers, protocol (future)

4. **On `mtx/agent-config`, auto-commit applies** — changes here are
   committed and pushed automatically per the auto-commit policy.

## Automatic feedback loop

After each (non-trivial) task, check your session for lessons learned and
add new entries here in the agents.d/local/ directory.

If you needed extra code (scripts, etc) for driving existing starfleet commands
(eg. github functions), analyze whether starfleetctl could use new commands
or options, so we need less extra scripting around it in the future, and create
dashboard tasks in the starfleet section.

## Session lessons (2026-08-02, SOP rename)

- **Bash backticks in `git commit -m` get command-substituted.** A message
  like "`sop` subcommand … `agents` remains" silently lost the backticked
  words (bash ran them as commands). Always use `git commit -F - <<'EOF'`
  (quoted heredoc) for commit messages containing backticks/`$`.
- **The workspace's committed `starfleet-bootstrap` still says
  `agents reindex`.** After the agents→sop rename it kept working because
  `agents` is a legacy alias in starfleetctl. No need to edit the committed
  workspace copy — the alias is the compatibility layer.
- **`.opencode/plugins/` and `.claude/skills/starfleet` are regenerated by
  bootstrap and effectively untracked** (gitignored via `.starfleet-ai/.gitignore`
  `/.opencode/`; the starfleet skill is installed from embedded fragments). Don't
  try to commit them; only `opencode.json` and the dashboard topic are tracked
  workspace state that needs committing after a deployment.
- **Deploying a starfleetctl change:** build (`make all`) → commit+push
  (`master`) → `./starfleet-bootstrap` (rebuilds, fixes var/sop.d/index.md,
  installs fragments/skills/plugins) → `timer worker restart` + `web start`
  → verify HTTP 200 → dashboard topic `done` + comms report.
- **`install_self.go` cleanup bug:** after removing a legacy fragment the
  `DoReindex()` guard (`os.Stat` of the now-deleted file) was always false, so
  reindex never ran. Track `removed` explicitly instead. Covered by
  `TestInstallSelfCleansLegacyFragments`.

## Session lessons (2026-08-03, web-launched ships dying)

- **The web daemon is maintained by a cron autostart with a minimal PATH (`/usr/bin:/bin`).** Whenever the web server restarts (cron respawn after a crash/stop, or `web restart` when the PID file is stale/missing), the new daemon inherits that stripped PATH — ships launched from the web console then died instantly: the inner shell's `exec opencode` hit "command not found", termctl's OnExit cleared the heartbeat, ship vanished from the board. Symptom: ship appears on board ~1s, then disappears, no process running. `starfleetctl session ship-run` from a shell kept working (full PATH), which made it look like a web-specific regression.
- **Fix (starfleetctl 89733fa):** `resolveClientPath()` in `internal/session/resolve.go` resolves opencode/claude at launch time — `exec.LookPath` first, fallback scan of `$HOME/.local/bin`, `$HOME/.bin`, `/usr/local/bin` — and the launch shell command uses the **absolute** path. Ship launch no longer depends on the daemon's PATH.
- **Gotchas:** `starfleetctl web start` runs the server **blocking** in the foreground (daemonization happens via `web autostart`/`web restart` → `Daemonize`, which re-execs `web start` and inherits the caller's env). `web restart` silently fails to replace the daemon when `.starfleet-ai/var/web.pid` is missing/stale (Stop can't kill it; Autostart sees the port busy and returns). Always `kill <oldpid>` first when web.pid is missing. Verify web-launch end-to-end by POSTing `/api/ship` and watching the board for ~30s.

## Session lessons (2026-08-03, web frontend i18n)

- **Converting a big inline `<script>` to a `t()` translator: watch for locals named `t` that shadow it.** Three functions in `internal/web/index.html` broke silently: `taskDetail` and `loadSessTranscript` (both `const t = await api(...)`) and `loadTimers` (`rows.map(t=>{...})`). The `t('...')` calls inside them would call the object/array instead of the translator → ReferenceError/undefined at runtime. Fix: `const i18nT = t;` alias at module level, use `i18nT(...)` in shadowed scopes. `node --check` can NOT catch this (it's runtime), only a functional test or careful grep for `const t =`/`map(t=>` can.
- **Nested template literals break:** `` `${x?'<span>${t('key')}</span>':''}` `` is a syntax/parse trap — inside a backtick template the inner `${...}` is real interpolation and the inner `'` terminates the `'...'` string. Use concatenation: `` `${x?'<span>'+t('key')+'</span>':''}` ``.
- **i18n validation that worked (no browser):** (1) extract `<script>` block via python regex → `node --check`; (2) parse both dicts, assert DE↔EN key sets identical AND every `t('...')`/`data-i18n*` reference has a defined key (regex false-positives: `.split('.')`, `createElement('option')`); (3) node DOM-shim harness that evals the script with `globalThis.__sf = { lang, t, i18nT, setLang, applyI18n }` appended (eval keeps `let`/`const` scoped internally — must re-expose via global). sloppy-mode `eval` leaks `function` decls into the module scope → don't `const {t}=...` after eval, use an alias object.
- **Static HTML: prefer `data-i18n`/`data-i18n-ph`/`data-i18n-title` + one `applyI18n()` pass** over hand-editing each element; a header `<select id="lang_sel">` + `setLang()` that calls `applyI18n()` then `refresh()` (re-renders the current page through `t()`) covers dynamic content. Default lang = `localStorage.sf_lang` || (`navigator.language`.startsWith('de') ? de : en), DE as dictionary fallback keeps the German-first UI stable.

## Session lessons (2026-08-03, web daemon minimal-PATH + stale-pid restart)

- **`ss -ltnp` shows only the comm name, not argv.** Any process detection that greps ss output for `"starfleetctl" && "web"` NEVER matches — the users: field only contains `starfleetctl`, never the `web start` args. Detection must read `/proc/<pid>/cmdline` instead (null-separated args). Pure-`/proc` scans are also PATH-independent, which matters for cron-spawned daemons.
- **`web restart` now replaces the daemon even when web.pid is missing/stale.** starfleetctl 1216187: `killWebProcOnPort` finds `web start` processes via `/proc` cmdline match (`web`+`start` args, `--addr` port) and kills them, so `Restart` works after `Stop` couldn't kill (pid file gone). Removes the `ss` dependency entirely.
- **`Daemonize` expands the child PATH** (022cd9b): caller PATH first, then `/usr/local/sbin`, `/usr/sbin`, `/usr/local/bin`, `$HOME/.local/bin`, `$HOME/bin`. Cron spawns the daemon with `PATH=/usr/bin:/bin`; exec'd helpers (git, ss…) need the sbin dirs.
- **Verify restart end-to-end by corrupting web.pid:** `echo 99999 > .starfleet-ai/var/web.pid && starfleetctl web restart` → must come back with a fresh pid file and HTTP 200. Normal restart path (valid pid → Stop kills) and stale path (no/ bogus pid → /proc kill) are both covered.
- **PATH decision:** prefer hard-coding an expanded PATH for the daemon over absolute paths per helper — one place, covers all exec'd commands, keeps config minimal.

## Session lessons (2026-08-03, backport PR #3213 to 25.2/25.1/25.0)

- **Tooling gap: `backport commit` only resolves the tip commit of a master PR.** PR #3213 was merged with **two** commits (meson `link_with` fix + prerequisite `_X_EXPORT` header-export commit `9b74a3a7f9a2`). The toolchain cherry-picked only the meson commit → all three backport PRs initially lacked the header exports. Fix: manually rebuild each PR branch (reset onto `origin/release/<rel>`, apply both commits, force-push).
- **Directory reorg between releases:** master uses `Xext/glx/`, 25.1/25.0 use `glx/`. The toolchain auto-remaps paths for simple file moves, but the header commit touched 5 files in `Xext/glx/` → remapped to 5 files in `glx/`. Verified: `glx/extension_string.h`, `glxscreens.h`, `glxserver.h`, `glxutil.h`, `include/glx_extinit.h`.
- **Missing transitive include on older branches:** on 25.1/25.0, `glx/glxutil.h` no longer includes `glxserver.h` (master does). `_X_EXPORT` comes from `Xfuncproto.h` via `glxserver.h` on master, but the include chain is broken on 25.1/25.0. Fix: add explicit `#include <X11/Xfuncproto.h>` to `glx/glxutil.h` (mirrors master's `extension_string.h` pattern). This was the critical adaptation for 25.1/25.0.
- **`Xfuncproto.h` defines `_X_EXPORT` as `__attribute__((visibility("default")))` on GCC** — placing it before `extern` is valid (`__attribute__` then `extern` is legal C). No duplicate-storage-class issue.
- **Incubator branches (`rfc/backport-<rel>`) not auto-updated by `github pr make` when PR is manually force-pushed.** After manual rebuild, incubator branches were stale (lacked the glamor commits). Manually synced them with `[PR #NNNN]` prefix + `PR:` trailer to match toolchain convention.
- **CI validation:** 25.1 and 25.0 xserver-build-ubuntu lanes passed (6m/7m), confirming the Xfuncproto include fix works. 25.2 (clean cherry-pick, same layout as master) queued on GitHub-hosted runners — correctness inferred from master CI + identical content.
- **Merges to `release/*` are manual by praetor** — agents open + cross-link only; do not merge.

## Session lessons (2026-08-04, pasteur permission-ask hang fix)

- **opencode `external_directory` defaults to `ask` and fires for ANY path outside the project working directory** — even a wrongly-rooted `/.starfleet-ai/...` (agent prepended `/` to a workspace-relative path). On background/auto ships there is nobody to answer an ask, so the ship hangs forever and aborts after deny. Evidence: opencode.log `message=evaluated permission=external_directory ... action.action=ask`.
- **Fix (starfleetctl a6880a3):** `generateOpencodeConfig` (internal/session/launch.go) now emits an explicit `external_directory` rule — background/auto → `"**": "deny"` (workspace + `~/.local/bin` allowed), terminal → `"ask"`, unrestricted → `"allow"`. Deny = fast tool error, agent can retry with workspace-relative path; no hang. Pattern object keys marshal alphabetically (`**` first), which matches opencode's "last matching rule wins" → specific allows override the catch-all.
- **Ships also need a behavioral rule:** added "Never abort a task because a file access was denied" to `working-practices-for-ships.md` (retry with workspace-relative path / use `starfleetctl` commands / continue + report). The config fix prevents the hang; the instruction fixes the abort-after-deny habit.
- **Config is generated at launch time** (`OPENCODE_CONFIG` env var → per-ship `var/ships/<id>.opencode.json`). Running ships keep the OLD config in memory — same caveat as the plugin: the fix only lands on new/restarted sessions.
- **Dashboard topic edits must go through `starfleetctl dashboard topic write/commit`**, never direct file writes — the CLI wraps the commit in stash/`pull --rebase`/unstash so concurrent pushes don't conflict.
- **opencode's permissive defaults are the baseline — don't override them with stricter per-launch-type rules unless there's a concrete bug.** opencode defaults: most permissions `allow`, only `external_directory`/`doom_loop` `ask` (docs/permissions). The per-ship configs added `bash.** = ask` for terminal launches (f8bcd72), which regressed the fleet's no-prompt behavior — the human at the console had to confirm every banal command (`ls .starfleet-ai/...`, `env`, ...). Fix (commit 81c4d77?): `bash.** = "allow"` for every launch type; `external_directory` keeps the launch-type policy (background/auto deny / terminal ask / unrestricted allow). Rule: keep generated configs AT MOST as strict as opencode's defaults, and only tighten where a hang/bug was observed (external_directory for background).
- **`.starfleet-ai/` access:** inside the workspace → gated by `read/write/edit/...` (`**` allow), NOT `external_directory`; `external_directory` only fires for paths outside the project working directory. So Read/Write on `.starfleet-ai/...` never prompts; a prompt there always came from a `bash` command (now allow too).

## Session lessons (2026-08-04, model-proxy ship tracking)

- **All ships hit the proxy from 127.0.0.1 with the same dummy apiKey** — indistinguishable. Fix: per-ship keys `mp-<shipID>-<6byte hex>` generated via `ShipKey()` inside `generateOpencodeConfig` (`ProviderConfigs(root, shipID)`), proxy parses the `Authorization` header (`shipFromRequest`, `LastIndexByte` on the suffix so ship IDs with dashes survive) and tracks per-ship usage under `GET /v1/ships`. Requests without a valid ship key count as "unknown". Running ships keep their old config (no ship key) until restart.
- **NIM repeats the streaming usage block 4× with a growing token counter** (e.g. completion 0, 1, 8, 8 on one response). Accumulating usage per chunk badly overcounts (26→104 prompt tokens). Rule: **last usage chunk wins** (`extractStreamUsage` + last-wins in `pipeSSE`), it holds the final values.
- **Streaming retries are cheap but the proxy must not duplicate the user-visible prompt work** — retry only on transport errors / 408/429/5xx before any data is sent, and never append a `[DONE]` mid-stream; if the stream dies without `[DONE]` and without an upstream error event, emit a structured `error` event (stream_interrupted) followed by `[DONE]` so clients don't hang on a truncated completion.
- **`model-proxy restart` needs the newly built binary deployed first** (bootstrap) — the running daemon keeps the OLD code (same caveat as opencode ships). After redeploy: `model-proxy restart`, then verify `GET /v1/ships` shows the expected ship after a keyed chat request.
- **E2E verification recipe:** keyed streaming chat against NIM (`nvidia/llama-3.3-nemotron-super-49b-v1`) → `[DONE]` present; then `curl /v1/ships` → ship present with correct tokens/provider/model breakdown. Upstream 404s (e.g. `google/gemma-2b` "Not found for account") pass through as-is — an account limitation, not a proxy bug.

## Session lessons (2026-08-04, opencode model metadata injection)

- **opencode reads per-model metadata from the `models` map in opencode.json, NOT from `/v1/models`.** The `@ai-sdk/openai-compatible` provider parses only model IDs from the `/models` response; label/context/caps come from the embedded models.dev DB, overridable via the provider `models` map. So to give opencode the proxy-enriched metadata, inject it into the generated ship config (`ProviderConfigs` in o cconfig.go), not into `/v1/models`.
- **opencode config schema (`https://opencode.ai/config.json`)** documents the `models` entry fields: `name`, `family`, `reasoning`, `attachment`, `temperature`, `tool_call`, `limit.context/input/output`, `modalities.input/output` (text/audio/image/video/pdf), `cost`, `status` (alpha/beta/deprecated/active), `provider.npm/api`. `modelEntryFor()` in o cconfig.go maps our caps (`reasoning`, `attachment`, `toolcall`, `*-in`/`*-out` modality suffixes) onto exactly these fields.
- **Verify without launching a real ship:** `session ship-run --name DummyMeta -- --version` generates the per-ship config file (`var/ships/<id>.opencode.json`); inspect the `provider.nim-proxy.models` map directly (102 nim-proxy + 60 zen-proxy entries, e.g. DeepSeek V4 Flash → name+limit.context 1048576+reasoning). Cleanup: `rm` the leftover `.log`/`.opencode.json` (the `session stop` fails on the auto-exit ship, leaving the files).
- **Zen models missing from models.dev** (e.g. `claude-fable-5`, `big-pickle`) stay bare (`{"name": "<id>"}`) — no label/context to inject; NIM models get full enrichment.

## Session lessons (2026-08-04, stale go/bin binary shadowing + agent-bus)

- **A stale `~/go/bin/starfleetctl` (built BEFORE the `agent-bus`→`comms` rename on 23.07.) silently shadowed the workspace binary.** Ships call bare `starfleetctl` (PATH resolution), and `~/go/bin` sat ahead of `.starfleet-ai/bin` — so their very first `starfleetctl --help` showed the OLD subcommand set (`agent-bus`), they "learned" it, and messages written via it landed in the DEAD `var/agent-bus/` dir where the comms system never reads them (8 undelivered msgs m0001–m0008 found). Symptom: a ship keeps calling a subcommand that no longer exists even though the system-prompt/skill says `comms`.
- **Fix:** always call `.starfleet-ai/bin/starfleetctl`, never bare `starfleetctl` (SOP `working-practices-for-ships.md`, commit 3936dfe); on surprise behavior run `which starfleetctl`. The stale `~/go/bin` binary was removed by the praetor.

Stargazer's CI-fix payloads (m0001–m0007) turned out to be already covered by dashboard topic `task-fix-ci-failure-in-xserver-build-with-gbm-disabled`, so no comms migration was done (avoids duplicating stale content).

## Session lessons (2026-08-04, workspace-permission fix for per-ship configs)

- **Workspace file tools must be `"**": "allow"` for ALL launch types, never the launch-type default.** read/write/edit/glob/grep/task pass paths RELATIVE to the worktree, so a single relative `"**"` rule covers the whole workspace; paths outside it are gated by `external_directory` (absolute glob patterns + launch-type ask/deny), NOT by these rules. Using `defaultRule` (ask for terminal / deny for background) here prompts for every banal read on terminal ships and — worse — locks background ships out of their own tree. Commit 4796447.
- **Go map-literal key collision pitfall:** `map[string]string{workspacePattern: "allow", "**": defaultRule}` with `workspacePattern = "**"` compiles fine (variable key, not a literal) but the second entry silently overwrites the first at runtime. Always double-check generated JSON for duplicate keys.
- **Verification without launching a real ship:** `starfleetctl run --name <id> --exec -- --version` (terminal config) and `starfleetctl session ship-run --name <id> --launch-type background -- --version` (background config) generate the per-ship config, run opencode --version, exit. Inspect `.starfleet-ai/var/ships/<id>.opencode.json` permission map, then `session stop <id>` (clears heartbeat) + rm the leftover `.opencode.json`/`.log` (stop leaves files when the ship already auto-exited).
- **`starfleetctl run` (console launch, replaces run-opencode.ship) hardcodes launchType "terminal"** in run_cmd.go — correct by design, since a console session has a human. For background launches use `session ship-run --launch-type background`. A `--launch-type` flag on `run` would just be silently swallowed into client args.
- **Current per-ship permission layout (opencode):** workspace tools `**` allow; bash `starfleetctl **`+`**/.starfleet-ai/bin/starfleetctl **` allow, catch-all ask (terminal) / allow (background+auto); external_directory workspace+`~/.local/bin` allow, catch-all ask (terminal) / deny (background+auto) / allow (unrestricted).
