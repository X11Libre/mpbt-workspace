### #3779 — auf allen drei identisch vorhanden

Der Fehlerpfad steht in allen drei Branches wortgleich:

```c
 bail:
    for (i = 0; i < numRI; i++)
        xfreeData(&ri[i].reg);
    free(ri);
    return RegionBreak(badreg);      /* badreg->data ist stale -> doppelt frei */
```

`xfreeData(&ri[i].reg)` gibt Speicher frei, auf den `badreg->data` noch zeigt.
`RegionBreak(badreg)` benutzt `badreg->data` weiter. Speichersicherheit,
client-erreichbar (RegionValidate laeuft auf Client-Regions via XFixes/XComposite).

### #3776 — hier liegt die Actual-Arbeit

Die Datei ist auf den Branches **nicht** am selben Ort:

| Branch | Pfad |
|---|---|
| master, 25.2 | `Xext/xinput/xiquerydevice.c` |
| **25.1, 25.0** | **`Xi/xiquerydevice.c`** |

Ein mechanischer Cherry-Pick des Master-Commits schlaegt auf 25.1/25.0 fehl. Der
Fix muss dort neu abgeleitet werden: `swapl(&info->flags);` nach
`swaps(&info->scroll_type);` in `SwapScrollInfo`. **Und** die Testdatei
`test/xi2/protocol-xiquerydevice.c` muss mit, sonst passt der Test-Harness nicht
mehr zum Server und der Test schlaegt umgekehrt fehl.

### #3777 — Test-Integritaet, kein Produkt-Fehler

`int exit_code = -1;` auf allen drei Branches, `goto child_failed` springt weiter
ueber die Zuweisung. Folge: ein per Signal gestorbener Test meldet PASS, wenn ein
frueherer Test bestanden hat. Kein User betroffen, aber die Release-Lanes sind
dadurch blind fuer Crashes. Backport empfohlen, Prioritaet niedriger als 3779/3776.

## ABNAHMKRITERIUM (vom Maintainer, 2026-10-01) — Dashboard je PR, verlinkt

Fuer **jeden** der 9 PRs gilt ohne Ausnahme:

1. **Ein Dashboard-Topic pro PR**, nicht pro Batch. Ein PR ohne eigenes Topic
   gilt als nicht erledigt, egal ob der Code stimmt.
2. Das Topic muss den PR verlinken (Slug, Nummer und Commit-SHA des Backports),
   damit der Zusammenhang ohne Raten auffindbar ist.
3. Das Batch-Topic (dieses hier) verlinkt **seinerseits** jedes der 9 Topics.
   Wer die Liste durchgeht, muss von hier aus zu jedem PR navigieren koennen.
4. Im PR selbst (Body oder Label-Kommentar) muss der Topic-Slug stehen. Ein PR,
   der nicht auf sein Topic zurueckverweist, gilt als nicht verlinkt.
5. Erst wenn Commit **und** Topic **und** Verlinkung in beide Richtungen stehen,
   darf ein Haken in der Checkliste oben gesetzt werden. Ein Haken ohne Topic ist
   kein Beleg, das ist eine Behauptung.
6. `dashboard topic update` ist defekt und ueberschreibt Felder — Topic-Aenderungen
   ausschliesslich ueber `dashboard topic write <slug> <datei>` mit vollstaendigem
   Frontmatter plus `dashboard topic commit`. Rohdateien unter `dashboard/topics/`
   werden nicht angefasst, das ist untersagt.

## Regeln fuer alle drei

- **release/* wird NIE automatisch gemergt.** Review, Kommentar, Label — dann
  Stopp. Merge macht der Maintainer von Hand. `bot-review-passed` ist ein
  Review-Votum, keine Merge-Erlaubnis.
- Merge-Mode **rebase**, nie squash, nie merge-commit. Am xserver-Repo ist nur
  rebase erlaubt (`allow_squash_merge=false`, `allow_merge_commit=false`).
- Backport-Commits bekommen einen `Part-of:`-Trailer auf den Ursprung
  (bei xorg-Upstream: Link auf **ihr** MR, nicht auf unseren PR).
- Pro Branch ein eigener PR, eigener Branch. 9 PRs, nicht 3 mit je 3 Branches.
- `starfleetctl github pr` braucht `STARFLEET_GITHUB_REPO=X11Libre/xserver`,
  sonst adressiert es das Workspace-Repo (Bug, Laforge, m125521).
- Backport-Tracker pro Branch: `tracking/xorg/main-on-<branch>` bzw. der
  Backport-Tracker wird mitgezogen, damit er nicht zurueckfaellt.

## Offen

- Merger-Reihenfolge innerhalb eines Branches bei mehreren PRs, die dieselbe Datei
  anfassen (3776 beruehrt `xiquerydevice.c`, 3777 `tests-common.c` — keine
  Ueberschneidung, also unkritisch).
- Ob #3776 auf 25.0 überhaupt sinnvoll ist: `Xi/xiquerydevice.c` ist der alte
  Pfad, aber die Funktion existiert dort, also ja. Sollte der Backport dort Merge-
  Konflikte erzeugen, ist der Maintainer zu fragen, nicht zu raten.
