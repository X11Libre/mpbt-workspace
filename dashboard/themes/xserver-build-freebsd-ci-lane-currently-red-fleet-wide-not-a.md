Found while chasing a FreeBSD failure on PR #3258 (a trivial brace-only style change). **Correction of an earlier, too-hasty read of this same log:** initially misdiagnosed as a generic pkg-mirror network flake (the visible symptom, `'pkg update -f' failed (attempt N/3)`, looks exactly like one) — the *actual* error a few lines earlier in the log is `pkg: repository FreeBSD contains packages for wrong OS version: FreeBSD:14:amd64` / `Newer FreeBSD version for package zycore-c: package: 1404000, running userland: 1403000` / `Ignore the mismatch and continue? [y/N]:`. `.github/workflows/build-xserver.yml`'s three `vmactions/freebsd-vm@v1` blocks pin `release: "14.3"`, but FreeBSD's official package repo has rolled its `FreeBSD:14:amd64` ABI branch forward to (at least) 14.4-built packages — `pkg` refuses the mismatch non-interactively (no TTY in CI to answer the prompt) and the whole `pkg update -f` dies, so the job never reaches the actual build. **This will NOT clear itself on retry** (confirmed: reran twice, identical failure both times) — reruns only make sense for genuine transient flakes, not a fixed version mismatch. **Confirmed systemic** (checked two unrelated concurrent runs — `fbdev-explicit-rate` PR run 28787951202, plain `master` run 28740407536 — both red the same way), i.e. **every FreeBSD job on every PR and on `master` itself is currently broken** until the workflow is updated. **Fix opened: PR #3259** (`ci: freebsd: set IGNORE_OSVERSION=yes`, master, single commit) — chose the `IGNORE_OSVERSION=yes` stopgap over bumping the `release: "14.3"` pins (lower risk, doesn't change what OS version is tested, matches pkg's own suggested remedy from the error message). CI running on the fix PR itself as verification — the real proof is whether `xserver-build-freebsd` actually goes green there.

**Update: IGNORE_OSVERSION fixed the version-check, but a second, independent issue surfaced immediately behind it.** Once `pkg update -f` could proceed, the build itself failed: `meson.build:126:13: ERROR: Dependency lookup for xfont2 with method 'pkgconfig' failed` → `Package bzip2 was not found in the pkg-config search path` (`freetype2`'s own `.pc` lists `bzip2` in `Requires.private`, pulled in transitively by `xfont2`). First attempt — adding the `bzip2` package to the install list — did **not** fix it: the package installs `libbz2` + headers but, on this CI image, no `bzip2.pc` file at all (confirmed `env[PKG_CONFIG_PATH]` is correctly empty/default, ruling out a search-path problem — this is missing package metadata, not a missing library or a path issue). Second attempt, pushed: synthesize a minimal `bzip2.pc` at CI time (locating the actual installed lib/header paths via `pkg info -l bzip2` rather than hardcoding them) if `pkg-config --exists bzip2` fails. CI running on this third iteration now. If this doesn't clear it either, this needs FreeBSD-packaging-specific eyes rather than further blind guessing from here.
