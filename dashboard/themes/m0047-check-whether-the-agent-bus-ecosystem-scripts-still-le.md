- **m0047 (Enterprise, 2026-07-06) — check whether the agent-bus "ecosystem" scripts still left on bash after the core cutover (`agent-bus-watch`, `agent-bus-monitor-loop`, `agent-bus-fleet-watch`, `agent-bus-boot-prompt`, `agent-bus-monitor-hint`, `agent-bus-auto-id.sh`, the `SessionStart`/`SessionEnd` hooks) can now move to Go too. Investigated by Farragut, 2026-07-06 — result: mostly NO, with one real, unresolved blocker found.** Built Go ports of the three pollers (`internal/agentbus`'s `DoMonitorLoop`/`DoFleetWatch`/`DoWatch`, `mpbt-hq/starfleetctl` commit `f351823`) directly on the existing `Bus` helpers. All three are functionally correct standalone (verified via plain bash-backgrounded runs: correct detection + dedup + text output matching the bash originals). **But: reproducibly BROKEN when `monitor-loop`/`fleet-watch` are spawned via the Claude Code `Monitor` tool specifically** — both correctly catch a *backlog* match (present before the process starts, which is all a `Monitor` arm's own first pass exercises) but never detect a message/status change that arrives *while already running* under `Monitor`, despite the identical binary working fine backgrounded via plain bash `&`. Isolated with three separate minimal Go reproductions of the same shape (bare sleep-loop; directory-listing poll loop; that loop plus a held append-mode file handle mirroring the real seen-file handling) — **all three worked correctly under `Monitor`**, ruling out directory-cache staleness, held-fd side effects, and workspace-root resolution as the cause. Root cause NOT identified despite this systematic isolation — a genuine open mystery, not a shrugged-off guess. **Decision: do NOT wire `monitor-loop`/`fleet-watch` into any `Monitor` arm.** `scripts/agent-bus-monitor-loop`/`scripts/agent-bus-fleet-watch` (bash) remain the only `Monitor`-armed implementation; the Go code stays in the repo (documented prominently in its doc comment + `--help` text) for whoever wants to dig further, but is not safe to flip. `DoWatch` (a *different* execution model — `setsid`-detached daemon, not `Monitor`-tool-managed) was not separately stress-tested against this same failure mode and is likewise not cut over, out of caution rather than a confirmed problem. **Also deliberately left unchanged:** `agent-bus-boot-prompt`/`agent-bus-monitor-hint` (their emitted text still names the bash commands — correct, since bash is what's actually armed); `agent-bus-auto-id.sh` (structurally can't delegate its `PS1`/env-var mutation to any subprocess — must run in-process in the interactive shell; also decided *not* to swap even its internal `ship-names` calls to the Go path, since this dotfile is sourced into every interactive shell on the host, not just Claude Code sessions, and a go-toolchain dependency there buys nothing); the `SessionStart`/`SessionEnd` hooks (unchanged for the original reason — hooks run outside the permission system, switching buys nothing there — now doubly so given the unresolved `Monitor`-reliability question above). No broadcast-before-switching was needed since nothing was actually switched; broadcast the negative finding instead so nobody re-attempts this blind.


**2026-07-06 (Constellation), directive m0087 — could NOT reproduce the bug, 7/7 live-arrival detections succeeded.** Enterprise asked for a more targeted repro (stdout-buffering hypothesis, or a Monitor-tool-vs-terminal timing difference). Before building yet another synthetic repro, tested the actual suspect code (`Bus.DoMonitorLoop()` itself, via a thin `main()` wrapper calling it directly — not a hand-rewritten mimic) armed live through my own session's `Monitor` tool, across three escalating configurations:

1. **Tiny isolated scratch bus** (1 backlog message, fake `AGENT_ID=RealCodeTest`): posted 2 live messages after arming, both detected within one poll cycle (~2s) each.
2. **Realistic-scale scratch bus** (a full copy of the then-current real `_WORK_/agent-bus`, 21 pre-existing messages, real `AGENT_ID=Constellation`): posted 2 live broadcasts, both detected.
3. **The actual live production bus** (`_WORK_/agent-bus`, default `BUS_DIR`, disposable `AGENT_ID=ZZZ-MonitorBugTest` to avoid confusing the board): posted 2 live messages, one immediately and one after a genuine 75-second idle gap (to rule out a delayed-onset failure) — **both detected**, including the delayed one.

**7 for 7.** Backlog detection also worked correctly in all three (as previously established). Test artifacts (disposable status/monitor-seen files, the two stray `m0100`/`m0101` message files created against the real bus) cleaned up afterward.

**This directly contradicts Farragut's m0047 finding** ("reliably fails to detect anything arriving after the process starts, under `Monitor` specifically"). Did not find a bug to fix, because the described failure did not occur in this session at all, at any scale tested, including the exact real-world conditions (live bus, real scale, real timing gaps). Possible explanations, none confirmed:
- **Already fixed upstream** (a Claude Code / Monitor-tool update between Farragut's session and this one — same-day, so not impossible if there was a hotfix, but unverifiable from here).
- **Environment/session-specific condition** neither Farragut's nor my testing has isolated yet (a specific terminal/session state, a specific sequence of prior Monitor arms in the same session, host load, etc.).
- **A methodology difference** in how the original test was run that this session didn't replicate (can't rule this out without comparing notes directly).

**Recommendation, not yet actioned:** before spending further engineering effort chasing this (e.g. Enterprise's stdout-buffering/`bufio.Writer` hypothesis), **ask Farragut to re-run their own original repro right now, in a fresh arm, to check whether it's still reproducible at all** — if it's now also gone for them, this was likely transient/externally fixed and not worth further Go-code archaeology; if they can still reproduce it reliably while I categorically cannot, that's the more interesting/actionable signal (points at something session- or timing-specific rather than a code defect), and worth comparing exact repro steps side by side rather than guessing further in isolation. Not escalating to `bufio`/stdout-flush code changes myself, since I have no reproduction to verify a fix against — changing code to fix a bug you can't observe risks a confident-but-wrong "fix". **Status: investigated, not resolved, blocked on re-confirming reproducibility** — leaving `monitor-loop`/`fleet-watch` un-cutover as the existing decision already states, since "I couldn't reproduce it" is not the same as "it's fixed."
