- **m0047 (Enterprise, 2026-07-06) — check whether the agent-bus "ecosystem" scripts still left on bash after the core cutover (`agent-bus-watch`, `agent-bus-monitor-loop`, `agent-bus-fleet-watch`, `agent-bus-boot-prompt`, `agent-bus-monitor-hint`, `agent-bus-auto-id.sh`, the `SessionStart`/`SessionEnd` hooks) can now move to Go too. Investigated by Farragut, 2026-07-06 — result: mostly NO, with one real, unresolved blocker found.** Built Go ports of the three pollers (`internal/agentbus`'s `DoMonitorLoop`/`DoFleetWatch`/`DoWatch`, `mpbt-hq/starfleetctl` commit `f351823`) directly on the existing `Bus` helpers. All three are functionally correct standalone (verified via plain bash-backgrounded runs: correct detection + dedup + text output matching the bash originals). **But: reproducibly BROKEN when `monitor-loop`/`fleet-watch` are spawned via the Claude Code `Monitor` tool specifically** — both correctly catch a *backlog* match (present before the process starts, which is all a `Monitor` arm's own first pass exercises) but never detect a message/status change that arrives *while already running* under `Monitor`, despite the identical binary working fine backgrounded via plain bash `&`. Isolated with three separate minimal Go reproductions of the same shape (bare sleep-loop; directory-listing poll loop; that loop plus a held append-mode file handle mirroring the real seen-file handling) — **all three worked correctly under `Monitor`**, ruling out directory-cache staleness, held-fd side effects, and workspace-root resolution as the cause. Root cause NOT identified despite this systematic isolation — a genuine open mystery, not a shrugged-off guess. **Decision: do NOT wire `monitor-loop`/`fleet-watch` into any `Monitor` arm.** `scripts/agent-bus-monitor-loop`/`scripts/agent-bus-fleet-watch` (bash) remain the only `Monitor`-armed implementation; the Go code stays in the repo (documented prominently in its doc comment + `--help` text) for whoever wants to dig further, but is not safe to flip. `DoWatch` (a *different* execution model — `setsid`-detached daemon, not `Monitor`-tool-managed) was not separately stress-tested against this same failure mode and is likewise not cut over, out of caution rather than a confirmed problem. **Also deliberately left unchanged:** `agent-bus-boot-prompt`/`agent-bus-monitor-hint` (their emitted text still names the bash commands — correct, since bash is what's actually armed); `agent-bus-auto-id.sh` (structurally can't delegate its `PS1`/env-var mutation to any subprocess — must run in-process in the interactive shell; also decided *not* to swap even its internal `ship-names` calls to the Go path, since this dotfile is sourced into every interactive shell on the host, not just Claude Code sessions, and a go-toolchain dependency there buys nothing); the `SessionStart`/`SessionEnd` hooks (unchanged for the original reason — hooks run outside the permission system, switching buys nothing there — now doubly so given the unresolved `Monitor`-reliability question above). No broadcast-before-switching was needed since nothing was actually switched; broadcast the negative finding instead so nobody re-attempts this blind.
