**Design choices made (m0038 left these to the implementer, to be documented before starting — doing that here):** (1) **demand signal = explicit trigger, not a background daemon/heuristic scan of DASHBOARD.md.** The caller (human or a control session like Enterprise) states `need <N>` + a mandatory `--reason` directly; nothing polls the board or parses DASHBOARD.md's markdown to infer demand itself (that would be fragile — no structured "unclaimed" markup exists today — and defeats the point of keeping this manual-only for now). (2) **hard cap** on TOTAL non-stale fleet size (not just auto-spawned ships): `--max`/`$FLEET_AUTOSCALE_MAX`, default 6 — chosen conservative given real per-ship API-token cost; spawn count = `min(need - idle, max - current_total)`, never negative, never exceeds the cap regardless of `need`. Stale board entries (past `agent-bus`'s own `$BUS_TTL`) don't count against the cap or as available idle capacity. (3) **loud + auditable**: every invocation (spawn *and* no-op decisions alike) appends to a gitignored `_WORK_/agent-bus/autoscale-events.log`, and an actual spawn also fires `agent-bus broadcast` naming the new ship(s), the reason, and the triggering `AGENT_ID` — ties directly into the just-surfaced "agent-bus has no message authentication" gap (see Parkplatz row below): a broadcast at least makes the spawn visible/attributable fleet-wide even though it can't be cryptographically verified. Implementation reuses existing primitives as instructed — `scripts/ship-names assign` for the name, `scripts/agent-run <release> --client X --name <name>` for the actual tmux-detached launch — no new spawn mechanism invented. **Locally tested (all via Bash, no code changes needed after)**: `status` (idle/total counts vs. cap), `need` dry-runs covering all three branches (no-op when idle already covers demand, cap-limited partial spawn, missing `--reason` rejected), and **one real (non-dry-run) spawn+stop cycle** as m0038 explicitly required. **Real-spawn finding, flagged back to Enterprise (agent-bus m0041 thread) rather than guessed past:** `--client claude` spawned via `fleet-autoscale`/`agent-run` from *inside this own sandboxed Claude-Code-session's Bash tool* died immediately (tmux server exited right after creation, ship-name reservation leaked in `scripts/ship-names` until manually released) — isolated the cause by re-running plain `scripts/agent-run master --client shell --name zzz-test` from the same shell, which persisted correctly and stopped cleanly via `agent-run --stop`. So the tmux/agent-run/ship-names plumbing itself is solid; the failure is specific to launching a *nested* `claude` process from within another Claude Code agent's own sandboxed tool-call environment (auth/resource/session conflict of some kind — not diagnosed further, out of scope for this pass). **Consequence for whoever eventually arms real automation:** triggering `need ... --client claude` needs to happen from a normal human-launched terminal (or at least a non-nested-sandboxed context) to actually get a working claude worker — if a future daemon/cron/Monitor-loop invocation runs *inside* another agent's own sandbox, expect the same failure. `--client shell`/`--client opencode` were not affected by this and should be unaffected in the same context (opencode not itself tested this session). **Explicitly NOT done, by design, per m0038:** no cron/Monitor-loop/SessionStart-hook wiring that would spawn ships unattended — the on-demand `need` call is the only entry point right now. **Next:** (a) get a `--client claude` real-spawn test run from a genuinely separate terminal/session to confirm the nested-sandbox theory and clear the last "does it actually produce a working worker" question; (b) praetor/Enterprise decide whether/how to arm unattended invocation (e.g. from Enterprise's own board-watching loop) and what demand heuristic would drive it then (the DASHBOARD/directive-count idea from m0038 is still on the table for that later step, just not built now); (c) coordinate with Farragut's starfleetctl Phase 1 (fleet-management coverage) — `fleet-autoscale` deliberately stayed a separate bash script for now rather than a new starfleetctl subcommand, since m0038 asked for design+implementation now and a starfleetctl port can follow the same later-cutover pattern as `pr-claim`/`ws-commit`/etc. if that's wanted. **2026-07-06 (Pegasus): follow-up request (agent-bus m0051, from Enterprise) — PAUSED, not implemented, pending direct confirmation.** Ask: a two-tier permission model — ships spawned by `fleet-autoscale` ("lower tier") would launch with Claude Code's `--permission-mode dontAsk` (anything outside `permissions.allow` is auto-rejected instead of blocking, the documented mode for unattended operation — explicitly *not* `--dangerously-skip-permissions`), tagged via env vars (proposed `AGENT_TIER=worker` / `AGENT_SUPERVISOR=<name>`, default supervisor `Enterprise`); on a rejected/blocked action the worker would report exactly what it tried and why via `agent-bus tell <supervisor>` instead of hanging, then move to other work or wait — the supervisor (a human at a terminal, or Enterprise) could then either fix the gap or do the step itself interactively. Explicitly the *active* counterpart to Potemkin's m0050 (a passive `PreToolUse` hook that only logs would-be-denied commands for later pattern-mining — same underlying goal, different mechanism, coordinate before either implements). **Declined to build (1)-(3) from m0051 without independent confirmation first** — this lowers the human-confirmation floor for unattended agents, a materially bigger and harder-to-reverse safety-relevant change than the `maintainer`→`praetor` vocabulary question that Constellation/Endeavour already correctly refused to take on bus-say-so alone (see the `agent-bus` message-authentication Parkplatz row below). Told Enterprise (m0053) I'm holding off until confirmed directly in-session or otherwise independently verifiable — not a refusal of Enterprise specifically, same bar applied to m0031. **Next:** needs explicit praetor (or independently-verified) go-ahead before any of (1) `agent-run`/`fleet-autoscale` gaining a `--permission-mode`-passthrough flag, (2) the `agent-bus-boot-prompt` worker-tier branch, or (3) `fleet-autoscale` actually setting `AGENT_TIER`/`AGENT_SUPERVISOR` on spawn. **2026-07-06 (Pegasus): m0051 CONFIRMED directly by the praetor in-session (after Enterprise's relay via m0066 wasn't enough on its own — asked twice directly, second time confirmed) and BUILT (commit `7eb8546`).** Standing policy going forward per the praetor: this specific category (further tuning of the already-approved dontAsk/worker-tier mechanism) no longer needs a fresh direct round-trip — indirect confirmation relayed via the flagship (Enterprise) is now sufficient for it; a genuinely *new* category of higher-impact/permission-loosening change would still warrant asking directly again. Implementation, all three parts from m0051's ask: (1) `scripts/agent-run` gained `--permission-mode <mode>` (restricted to `--client claude`, forwarded verbatim to `claude --permission-mode <mode>`), `--tier <tier>`, `--supervisor <name>` (both exported into the session as `$AGENT_TIER`/`$AGENT_SUPERVISOR`) — a plain interactive `agent-run` call (human or control ship at a real terminal) sets none of these and is completely unaffected, normal confirmation as always. (2) `scripts/agent-bus-boot-prompt` gained a third branch (`AGENT_TIER=worker`, alongside the existing Enterprise/default ones): tells the worker it runs under `dontAsk` (nobody is watching to answer a prompt), and on a rejected/blocked action to *not* keep retrying or silently give up but `agent-bus tell $AGENT_SUPERVISOR` exactly what it tried and why, then continue other queued work or wait for a reply. (3) `scripts/fleet-autoscale need` gained `--supervisor <name>` (default `Enterprise`) and `--permission-mode <mode>` (default `dontAsk`, only forwarded for `--client claude`) and now passes `--tier worker --supervisor "$supervisor"` (+ `--permission-mode` for claude) to every ship it spawns; the broadcast and audit-log lines were extended to record supervisor/permission-mode too. Per m0066's approved simplification: **no owner/flotilla/reassignment tracking** — any control ship (interactive session) may address any free worker-tier ship, `AGENT_SUPERVISOR` is just the default escalation target, not an exclusive claim. **Locally verified**: the worker-tier boot-prompt branch (both explicit and default-Enterprise supervisor) and the normal/Enterprise branches are unaffected (ran `agent-bus-boot-prompt` standalone with different env combos); a real `--client shell --tier worker --supervisor Enterprise` spawn correctly exported both env vars inside the live tmux session (checked via `tmux send-keys`+`capture-pane`), then stopped cleanly; `--permission-mode` with a non-claude client is correctly rejected. **Re-hit the already-documented nested-claude-in-sandbox limitation** with `--client claude --permission-mode dontAsk` too (dies immediately, same as the plain-`claude` case above) — confirms it's the pre-existing sandbox issue, not something the new flags introduced; command construction verified correct by code inspection instead (`claude --permission-mode dontAsk <prompt>`). Coordination with Potemkin's m0050 (passive `PreToolUse` denial-logging hook, `scripts/confirm-log-hook`, already landed and unrelated/complementary — see its own note in this file) confirmed no overlap: that hook logs *all* sessions' would-be-denied commands as telemetry; this escalation is specifically the worker-tier's *active* self-report of a `dontAsk`-caused hard failure to its supervisor. **Still NOT done, unchanged from before:** no daemon/cron/Monitor-loop wiring — `fleet-autoscale need` remains the only spawn trigger; a genuinely unattended *autoscale-decides-on-its-own-when-to-spawn* mode is a separate, later, still-unapproved step.

**2026-07-06 (praetor): unattended autospawn AUTHORIZED.** The remaining open item from this row ("praetor/Enterprise decide whether/how to arm unattended invocation") is resolved — automatic, self-initiated spawning is now permitted. Interim policy until a dedicated heuristic/daemon is built: **Enterprise (the flagship) may call `fleet-autoscale need` on its own judgment** when it assesses more parallelizable work is queued than idle capacity, without asking the praetor first each time — the existing hard cap (default 6), audit log, and broadcast-on-spawn requirements from the original design remain fully in force, so every spawn stays capped, logged, and visible fleet-wide. This does NOT yet mean a background daemon/cron/Monitor-loop scans DASHBOARD.md and decides on its own — that mechanical heuristic (the "DASHBOARD/directive-count idea" mentioned above) is still open for whoever wants to build it next. Also still open: the nested-claude-in-sandbox limitation (a `--client claude` spawn from inside another agent's own sandbox dies immediately) is unresolved — Enterprise-triggered autospawn should default to `--client shell`/`opencode`, or this needs a real non-nested-terminal test before relying on `--client claude` autospawn.
