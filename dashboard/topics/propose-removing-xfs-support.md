Praetor request, 2026-07-01. Full sweep of `dix/`, `os/`, `hw/`, `include/`, `meson.build`, man pages, and git history found **zero XFS-protocol-specific in-tree code**. `dix/dixfonts.c` implements only a generic, backend-agnostic FPE (Font Path Element) dispatch layer: `SetFontPathElements()`/`DetermineFPEType()` (`dix/dixfonts.c:1609,1655`) dispatch through a vtable (`fpe_functions[]`, type `xfont2_fpe_funcs_rec`) that is populated entirely by **libXfont2's own callback** (`register_fpe_funcs`, wired into `xfont2_client_funcs_rec` at `dix/dixfonts.c:2084-2108`) when the server calls `xfont2_init()`. The server never special-cases a `tcp/`/`fs/` path prefix anywhere — `hw/xfree86/common/xf86Config.c:190-236` only validates local-directory paths (`stat()` + `fonts.dir` check) and passes everything else through opaquely with just a comment ("Either an OK directory, or a font server name"). The `_init_fs_handlers`/`fs_block_handler`/`add_fs_fd`-style functions (`dix/dixfonts.c:2040-2076`, "fs" = "font system") are generic async-I/O/block-handler glue for *any* FPE backend, not X-Font-Server-protocol code. `meson.build`/`meson_options.txt` have no font-server option — `xfont2_dep` (`meson.build:126`) is a plain external pkg-config dep, not vendored (no `.wrap`/subproject). `man/Xserver.man` mentions "font servers" only generically, documents no `tcp/` syntax. No XLibre-authored commit ever touched font-server code (`git log --all -i --grep`: only pre-fork 2008 XFree86/X.org history, e.g. `6c78f1b736` removing `NOFONTSERVERACCESS`, which shows the FS backend was *already* external via libXfont even then). **Conclusion: "drop XFS support" is a `libXfont2`-side decision (drop its own `fs` FPE backend), entirely out of scope for an xserver PR — there is nothing removable here.** No draft PR opened per the task's explicit instruction not to fabricate one; recorded as closed/no-action instead. Contrast with the `xf86bigfont` row above, which *does* have real in-tree code and got its own removal-candidate PR. **Follow-up, 2026-07-01:** is the `Suspended`/`ClientSleep` async-completion plumbing in `dixfonts.c` (`doOpenFont`, `doListFontsAndAliases`, `_init_fs_handlers`) still needed without XFS? **Yes — it's required by libXfont2's generic FPE API, not XFS-specific.** Verified against `libxfont2` 1:2.0.6 source (`apt-get source libxfont2`): `Suspended` (`<X11/fonts/font.h>:72`, value 84) is a generic status code in the `FPEFunctions` vtable (`<X11/fonts/fontstruct.h>`, plain-`int`-returning callbacks every FPE backend implements) — `grep -rl Suspended src/` in libXfont2 hits **only** `src/fc/{fserve.c,fsconvert.c,fservestr.h}` (the font-server client backend); `src/{bitmap,builtins,fontfile,FreeType,util}/` — i.e. every backend xserver actually uses for local fonts — never return it. libXfont2's own `configure.ac` even has `--disable-fc` ("Support connections to xfs servers", default enabled) to compile the fs backend out entirely, without touching the vtable shape. So xserver must keep honoring `Suspended` generically (any FPE backend *could* return it per the API contract it links against), even though none of the backends it actually ships with ever do — this is libXfont2's ABI, not something XLibre can prune unilaterally
